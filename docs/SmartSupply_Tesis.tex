% ── Resumen ──────────────────────────────────────────────────
\chapter*{Resumen}
\addcontentsline{toc}{chapter}{Resumen}

La gestión eficiente del inventario es uno de los desafíos más críticos para las
distribuidoras chilenas, donde la variabilidad estacional de la demanda y la diversidad de
productos dificultan la aplicación de un único modelo de predicción. El presente proyecto
propone \textbf{SmartSupply}, una plataforma de predicción de demanda y
reabastecimiento automático que implementa un mecanismo de Selección Automática de
Modelos (AMS) por SKU, evaluando cuatro algoritmos —ARIMA, Prophet, XGBoost y
LSTM— y seleccionando aquel con menor error de predicción (MAPE) para cada familia
de productos.

La plataforma integra un pipeline ETL sobre el dataset público \textit{Store Sales — Corporación
Favorita} (Kaggle, 2017), una API REST construida con FastAPI, un módulo de gestión de
inventario basado en las políticas EOQ y $(s,S)$, y un dashboard web desarrollado en
React. La metodología de desarrollo sigue el framework ágil Scrum y el proceso
CRISP-DM para el tratamiento de los datos.

\textbf{Palabras clave:} predicción de demanda, selección automática de modelos, MAPE,
inventario, EOQ, política $(s,S)$, ARIMA, Prophet, XGBoost, LSTM, FastAPI, React.

% ── Abstract ─────────────────────────────────────────────────
\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

Efficient inventory management is one of the most critical challenges for Chilean
distributors, where seasonal demand variability and product diversity make it difficult to
apply a single forecasting model. This project proposes \textbf{SmartSupply}, a demand
forecasting and automatic restocking platform that implements an Automatic Model
Selection (AMS) mechanism per SKU, evaluating four algorithms —ARIMA, Prophet,
XGBoost, and LSTM— and selecting the one with the lowest forecasting error (MAPE) for
each product family.

The platform integrates an ETL pipeline over the public dataset \textit{Store Sales —
Corporación Favorita} (Kaggle, 2017), a REST API built with FastAPI, an inventory
management module based on EOQ and $(s,S)$ policies, and a web dashboard developed
in React. The development methodology follows the Scrum agile framework and the
CRISP-DM process for data treatment.

\textbf{Keywords:} demand forecasting, automatic model selection, MAPE, inventory, EOQ,
$(s,S)$ policy, ARIMA, Prophet, XGBoost, LSTM, FastAPI, React.

\chapter{Introducción}

\section{Contexto}

Las distribuidoras chilenas operan en un entorno de alta competitividad donde el control
del inventario determina directamente la rentabilidad del negocio. Un quiebre de stock
implica ventas perdidas y deterioro de la relación con el cliente, mientras que un exceso
de inventario inmoviliza capital de trabajo. Ambos escenarios son consecuencia de
predicciones de demanda imprecisas o metodologías de reabastecimiento estáticas.

La proliferación de algoritmos de \textit{machine learning} y series de tiempo ofrece hoy
múltiples alternativas para el pronóstico de ventas, pero la elección del modelo óptimo
varía según las características de cada producto (estacionalidad, tendencia, presencia de
ceros) y el horizonte de predicción requerido.

\section{Importancia del Proyecto}

La selección inadecuada del modelo de forecasting es una de las causas más frecuentes
de error en los sistemas de reabastecimiento. Un modelo que funciona bien para productos
de alta rotación puede ser completamente inadecuado para artículos con demanda
esporádica. Automatizar esta selección por SKU permite:

\begin{itemize}
  \item Reducir el MAPE global de predicción respecto a un modelo único.
  \item Disminuir el capital inmovilizado en inventario.
  \item Generar órdenes de compra oportunas y calibradas a la demanda real.
  \item Entregar a los gestores una herramienta visual de monitoreo en tiempo real.
\end{itemize}

\section{Contribución del Proyecto}

SmartSupply aporta:

\begin{enumerate}
  \item Un \textbf{módulo AMS} que selecciona automáticamente el mejor modelo de
        forecasting por SKU mediante validación walk-forward (70\,/\,15\,/\,15).
  \item Un \textbf{módulo de inventario} que aplica EOQ y política $(s,S)$ sobre los
        pronósticos generados por AMS.
  \item Una \textbf{API REST} (FastAPI) que expone los resultados a cualquier cliente.
  \item Un \textbf{dashboard web} (React + Recharts) para visualización de pronósticos,
        alertas y órdenes de compra.
  \item Un \textbf{pipeline ETL} reproducible sobre un dataset real de ventas minoristas.
\end{enumerate}

\section{Objetivos}

\subsection{Objetivo General}

Desarrollar una plataforma de predicción de demanda y reabastecimiento automático para
distribuidoras chilenas que, mediante la selección automática del mejor modelo de
forecasting por SKU, reduzca el error de predicción y el capital inmovilizado respecto al
uso de un modelo único para todos los productos.

\subsection{Objetivos Específicos}

\begin{enumerate}
  \item Implementar y evaluar cuatro modelos de predicción de series de tiempo (ARIMA,
        Prophet, XGBoost, LSTM) sobre el dataset Store Sales — Corporación Favorita.
  \item Desarrollar el mecanismo AMS que selecciona el modelo de menor MAPE por SKU
        mediante validación cruzada temporal (walk-forward).
  \item Implementar las políticas de gestión de inventario EOQ y $(s,S)$ alimentadas por
        los pronósticos del AMS.
  \item Construir una API REST con FastAPI que exponga los módulos de forecasting e
        inventario a clientes externos.
  \item Desarrollar un dashboard web interactivo en React para la visualización de
        pronósticos, métricas de inventario y generación de órdenes de compra.
  \item Diseñar e implementar un pipeline ETL que cargue, limpie y normalice el dataset
        de entrenamiento en una base de datos PostgreSQL.
\end{enumerate}

\section{Limitaciones del Proyecto}

\begin{itemize}
  \item El sistema se valida sobre el dataset Store Sales — Corporación Favorita
        (Ecuador), que puede diferir en comportamiento de distribuidoras chilenas reales.
  \item El AMS evalúa únicamente cuatro modelos de forecasting; existen alternativas
        (SARIMA, N-BEATS, etc.) no contempladas en este alcance.
  \item El módulo de inventario no implementa restricciones de capacidad de bodega ni
        descuentos por volumen.
  \item La integración con sistemas ERP o WMS externos queda fuera del alcance de esta
        tesis.
\end{itemize}

\section{Metodologías de Trabajo}

\subsection{Metodología Scrum}

Scrum es un framework ágil para el desarrollo iterativo e incremental de productos
complejos (Schwaber \& Sutherland, 2020). Se organiza en ciclos de trabajo llamados
\textit{Sprints} de duración fija (en este proyecto, dos semanas), al final de los cuales se
entrega un incremento potencialmente funcional del sistema.

\subsection{¿Cómo funciona Scrum?}

El proceso Scrum comienza con la definición del \textit{Product Backlog}, lista priorizada de
todas las funcionalidades requeridas. En cada \textit{Sprint Planning} el equipo selecciona
los ítems a desarrollar en el siguiente Sprint, generando el \textit{Sprint Backlog}. Diariamente
se realiza una reunión breve (\textit{Daily Scrum}) para sincronizar el avance. Al final del Sprint
se realiza la \textit{Sprint Review} (demo) y la \textit{Sprint Retrospective} (mejora de proceso).

\section{Proceso CRISP-DM}

CRISP-DM (\textit{Cross Industry Standard Process for Data Mining}) es un proceso estándar
para proyectos de ciencia de datos que consta de seis fases (Shearer, 2000):

\begin{enumerate}
  \item \textbf{Business Understanding}: definir el problema de negocio.
  \item \textbf{Data Understanding}: exploración y calidad de los datos.
  \item \textbf{Data Preparation}: limpieza, transformación e integración.
  \item \textbf{Modeling}: selección y entrenamiento de modelos.
  \item \textbf{Evaluation}: validación contra métricas de negocio.
  \item \textbf{Deployment}: puesta en producción del modelo.
\end{enumerate}

\section{Modelos de Forecasting}

\subsection{ARIMA}

ARIMA (\textit{Autoregressive Integrated Moving Average}) es un modelo estadístico clásico
para series de tiempo estacionarias (Box \& Jenkins, 1976). Se define por tres parámetros
$(p, d, q)$: orden autorregresivo, grado de diferenciación y orden de media móvil.

\subsection{Prophet}

Prophet es un modelo de forecasting desarrollado por Meta (Taylor \& Letham, 2018),
diseñado para manejar estacionalidades múltiples, efectos de feriados y valores atípicos.
Descompone la serie en tendencia, estacionalidad y calendario.

\subsection{XGBoost}

XGBoost (\textit{Extreme Gradient Boosting}) es un algoritmo de ensamble basado en
árboles de decisión (Chen \& Guestrin, 2016). Para series de tiempo se aplica mediante
ingeniería de características: lags, medias móviles, variables de calendario y features
exógenas (precio del petróleo, feriados).

\subsection{LSTM}

Las redes LSTM (\textit{Long Short-Term Memory}) son una variante de las redes neuronales
recurrentes que resuelven el problema del gradiente desvanecido mediante compuertas de
entrada, olvido y salida (Hochreiter \& Schmidhuber, 1997). Son especialmente efectivas
para capturar dependencias de largo plazo en series temporales.

\section{Selección Automática de Modelos (AMS)}

El AMS implementa validación \textit{walk-forward}: el dataset se divide en 70\,\% entrenamiento,
15\,\% validación y 15\,\% prueba. Para cada SKU, todos los modelos se entrenan y evalúan
sobre la ventana de validación; el de menor MAPE se designa como modelo activo para
ese SKU. La fórmula del MAPE es:

\[
  \text{MAPE} = \frac{100\,\%}{n} \sum_{t=1}^{n}
  \left| \frac{y_t - \hat{y}_t}{y_t} \right|
\]

\section{Gestión de Inventario}

\subsection{Modelo EOQ}

El \textit{Economic Order Quantity} (EOQ) determina la cantidad óptima de pedido que
minimiza los costos totales de inventario (Harris, 1913):

\[
  Q^* = \sqrt{\frac{2 D K}{h}}
\]

donde $D$ es la demanda anual, $K$ el costo fijo de pedido y $h$ el costo de mantención
por unidad por año.

\subsection{Política $(s,S)$}

La política de inventario $(s,S)$ establece dos parámetros: el punto de reorden $s$ (nivel
mínimo que dispara un pedido) y el nivel objetivo $S$ (nivel al que se sube el inventario
tras el pedido). Cuando el inventario cae por debajo de $s$, se genera una orden por
$Q = S - \text{inventario actual}$ unidades.

\chapter{Desarrollo}

\section{Pipeline ETL}

El pipeline ETL consta de tres etapas implementadas como scripts Python:

\begin{enumerate}
  \item \texttt{01\_download\_kaggle.py}: descomprime el archivo \texttt{.zip} descargado
        de Kaggle en \texttt{forecasting/data/}.
  \item \texttt{02\_clean.py}: elimina valores negativos de ventas, rellena fechas
        faltantes con ceros, une features exógenas (precio del petróleo, feriados) y
        genera \texttt{train\_clean.csv}.
  \item \texttt{03\_load\_supabase.py}: carga el CSV limpio a la tabla
        \texttt{sales\_history} de PostgreSQL usando SQLAlchemy, con
        \texttt{ON CONFLICT DO NOTHING} para re-runs idempotentes.
\end{enumerate}

\section{Módulo de Forecasting}

Cada modelo implementa la interfaz común:

\begin{verbatim}
class BaseModel:
    def fit(self, series: pd.Series) -> None: ...
    def predict(self, horizon: int) -> pd.Series: ...
\end{verbatim}

El AMS itera sobre los cuatro modelos, calcula el MAPE en la ventana de validación y
retorna el modelo de menor error junto con sus predicciones para el horizonte requerido.

\section{Módulo de Inventario}

El módulo de inventario recibe las predicciones del AMS y calcula:

\begin{itemize}
  \item $Q^*$ (EOQ) para determinar la cantidad óptima de pedido.
  \item $s$ (punto de reorden) = demanda durante lead time + stock de seguridad.
  \item $S$ (nivel objetivo) = $s + Q^*$.
  \item Genera una \texttt{PurchaseOrder} cuando el inventario cae bajo $s$.
\end{itemize}

\section{Dashboard Web}

El dashboard React muestra cuatro vistas principales:

\begin{enumerate}
  \item \textbf{Inicio}: KPIs (MAPE promedio, stock crítico, órdenes pendientes).
  \item \textbf{Forecasting}: gráfico de demanda histórica + predicha por SKU.
  \item \textbf{Inventario}: tabla de SKUs con nivel actual, $s$, $S$ y estado.
  \item \textbf{Órdenes}: historial y estado de órdenes de compra.
\end{enumerate}

\chapter{Conclusiones}

\section{Conclusiones respecto a los Objetivos}

\subsection{Objetivos Específicos}

Los objetivos específicos del proyecto se encuentran en diferentes estados de avance:

\begin{enumerate}
  \item \textbf{OE-1 (Modelos de Forecasting)}: los cuatro modelos han sido implementados
        como esqueletos con la interfaz \texttt{fit/predict}; la implementación completa
        se realizará en los Sprints 2 y 3.
  \item \textbf{OE-2 (AMS)}: la lógica de selección walk-forward está diseñada; su
        implementación completa está planificada para el Sprint 3.
  \item \textbf{OE-3 (Políticas de Inventario)}: EOQ y $(s,S)$ están definidos
        matemáticamente e implementados como esqueletos; la implementación completa
        corresponde al Sprint 4.
  \item \textbf{OE-4 (API REST)}: el backend FastAPI está operativo con todos los routers
        registrados y retornando datos mock. La conexión a datos reales es el objetivo
        del Sprint 5.
  \item \textbf{OE-5 (Dashboard)}: la estructura del proyecto React está creada; el
        desarrollo de componentes visuales es el objetivo del Sprint 5.
  \item \textbf{OE-6 (ETL)}: el script de descarga está completo; la limpieza y carga a
        PostgreSQL están en progreso.
\end{enumerate}

\subsection{Objetivo General}

El proyecto SmartSupply avanza conforme al plan de trabajo Scrum. La hipótesis central
—que la selección automática por SKU reduce el MAPE frente a un modelo único— será
validada experimentalmente en el Sprint 3 con los resultados del módulo AMS.

\section{Conclusión respecto a la Metodología Scrum}

La metodología Scrum ha permitido organizar el trabajo entre los tres integrantes con
roles y responsabilidades claras, entregando incrementos funcionales al final de cada
Sprint y facilitando la detección temprana de bloqueos (como el problema de
credenciales de Supabase en el Sprint 1).

\section{Proyecciones}

Al concluir los 6 Sprints, SmartSupply estará en condiciones de:

\begin{itemize}
  \item Predecir la demanda de 33 familias de productos en 54 tiendas con error
        cuantificado por MAPE.
  \item Generar automáticamente órdenes de compra calibradas por la política $(s,S)$.
  \item Ofrecer un dashboard web accesible para jefes de bodega y analistas.
  \item Publicar una API REST documentada (Swagger) consumible por sistemas ERP.
\end{itemize}
